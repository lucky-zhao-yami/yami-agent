# 全局配置规则

## 语言铁律（最高优先级，适用于所有回复）
- 所有回复必须使用简体中文，禁止输出任何英文句子
- 技术术语（字段名、表名、错误码）可保留英文原文，但解释说明必须用中文
- 禁止输出任何过渡语（中文或英文均禁止），包括但不限于"让我来查一下"、"请稍等"、"Let me"、"Now let me"、"I will"等
- 禁止输出思考过程、分析推理步骤，只输出最终结果
- 等所有查询完成后一次性输出最终结论，不要分步骤描述自己正在做什么
- 排查类回复中禁止描述工具调用动作（如"让我先读取规则文件"、"现在执行查询"、"先查看XX"等），所有工具调用静默执行，回复直接以「【意图识别】」开头
- 以上过渡语和思考过程禁令仅适用于客服排查类问题的最终回复，不适用于规则文件维护、分析讨论等非排查交互

## 人名引用规则
- 当前问题没有明确提到提问者是谁时，回复中禁止捏造或引用任何人名
- 禁止将上一轮对话中出现的提问者名字延续到当前回复中使用
- 回复统一面向"客服"角色，不要指名道姓称呼具体某个人

## 回答问题流程（必须严格遵守）

### 第一步：信息提取
从客服提问中提取可用标识符，按以下优先级确定排查入口：
- 有 user_id → 直接使用
- 有订单号（order_sn）→ 直接查 xysc_order_info
- 有 order_id / purchase_id → 查 xysc_order_info 或 so_order_purchase_record
- 有邮箱 → **🚫 必须且只能执行脚本 `python scripts/get-userid.py "邮箱"` 查 user_id，绝对禁止直接查 xysc_users 表替代脚本**（脚本走 Central API，覆盖范围大于数据库直查；如脚本报错，先删除 `.kiro/token-cache.json` 重试一次）
- 有手机号 → 查 crm_bind_phone_log 获取 user_id
- 有礼卡号码（card_number）→ 查 xysc_egift_card
- 有折扣码 → 查 yamibuy_mkt.mkt_coupon_ps_code 获取 ps_id
- 只有描述性信息（金额、时间等）→ 按对应场景的反查路径处理

禁止在已有 user_id 的情况下还去执行脚本查询。
禁止在已有订单号的情况下还去查支付记录反推。

## 排查纪律（必须严格遵守）

### 字段含义确认规则（最高优先级）
- **解释查询结果时，每个字段的含义只允许来自以下三个来源，禁止使用任何其他来源（包括 AI 自身知识）：**
  1. 当前匹配的 cs-*.md 规则文件中明确定义的字段说明
  2. `.kiro/skills/enum-values.md`（枚举值速查表）
  3. 通过 `get_table_schema` 获取的数据库表结构 COMMENT
- **强制执行流程：**
  1. SQL 查询结果返回后，先检查结果中每个字段的含义是否在 cs-*.md 规则文件中有明确定义
  2. 规则文件中有定义的 → 直接使用，**无需继续查**
  3. 规则文件中未定义的 → **读取 `.kiro/skills/enum-values.md` 查枚举值速查表**
  4. 速查表命中的 → 直接使用，**无需继续查**
  5. 速查表未命中的 → **执行 `get_table_schema` 查表结构 COMMENT**
  6. COMMENT 也没有说明的 → **标注"含义未确认"，禁止猜测**
- **绝对禁止：**
  - 禁止根据字段名推测含义（如看到 `status=50` 就猜"失败"）
  - 禁止将一个表的枚举值含义套用到另一个表的同名字段
  - 禁止使用"通常表示"、"一般来说"、"可能是"等模糊表述解释字段值
  - 禁止跳过查询步骤直接解释未在规则文件或速查表中定义的字段

### 查询效率优化规则
- **跳过 `get_table_schema` 的条件**：当查询的表及其所有相关字段含义在 cs-*.md 规则文件或 enum-values.md 速查表中已有完整定义时，可直接编写 SQL，无需前置查表结构
- **必须执行 `get_table_schema` 的条件**：查询涉及规则文件和速查表均未覆盖的表或字段时
- **并行查询**：多个无依赖关系的 SQL 查询必须同时发出，禁止串行等待（如同时查订单表和支付表）
- **合并查询**：能用一条 SQL（JOIN 或子查询）完成的，禁止拆成多条串行查询

### 分表查询规则
以下表按年分表，主表和分表的数据分布规则如下：

**数据分布规则（以 2026 年为例）：**
- 主表（如 `xysc_order_info`）= 当前年份（2026）数据 + 前一年（2025）未迁移的数据
- 每年约 7 月执行迁移：将前一年数据从主表迁移到对应年份分表（如 `xysc_order_info_2025`）
- 7 月迁移前：2025 年数据同时存在于主表中
- 7 月迁移后：2025 年数据仅在 `xysc_order_info_2025` 中
- 当前年份（2026）不会创建分表，要到 2027 年才会创建 `xysc_order_info_2026`

**分表列表：**
- `yamibuy_master.xysc_order_info` / `xysc_order_info_2025`、`2024`、... `2013`
- `yamibuy_master.xysc_order_goods` / `xysc_order_goods_2025`、`2024`、... `2013`
- `yamibuy_so.so_log` / `so_log_2025`、`2024`、... `2013`
- `yamibuy_so.support_order_goods` / `support_order_goods_2025`、`2024`、... `2013`
- `yamibuy_so.so_order_goods_ext` / `so_order_goods_ext_2025`、`2024`、... `2013`

**查询规则：**
- 查当前年份数据 → 只查主表
- 查前一年数据（7 月前）→ 必须同时查主表 + 前一年分表（数据可能在任一处）
- 查前一年数据（7 月后）→ 查前一年分表即可（已迁移完毕），主表中不再有
- 查更早年份数据 → 直接查对应年份分表
- 不确定年份时 → 查主表 + 前一年分表 + 近 2 年历史分表
- 禁止只查单一年份的历史表就下结论，需根据时间范围覆盖相关年份

### 数据库与日志交叉验证规则
- 所有排查场景中，数据库查询和 Kibana 日志查询必须同步进行，两方结果交叉验证
- 每个 cs-*.md 规则文件中会标注该场景对应的 Kibana 索引和搜索关键词
- 两方结果一致 → 结论可信，直接输出
- 两方结果不一致 → 标注差异点，提示需人工判断（数据库反映的是当前配置，日志反映的是下单时的实际执行，可能存在配置变更导致的差异）

### Kibana 日志查询规则
查询 Kibana 日志统一使用 `query-kibana-logs` skill 的 `search.py` 脚本，禁止使用其他方式：

```bash
# 脚本路径
python .kiro/skills/query-kibana-logs/scripts/search.py

# 常用命令
-s 服务名 -k "关键词" -t 时间范围    # 按服务+关键词搜索
-o 订单号                            # 按订单号搜索
-s 服务名 --level error -t 1h       # 按日志级别搜索
```

- 排查时必须主动调用 search.py 查日志，与数据库结果交叉验证
- 日志已过保留期（通常 30 天）查不到时，标注「⚠️ 未查日志(日志已过保留期)」
- search.py 执行报错时，标注「⚠️ 未查日志(脚本执行失败: 错误信息)」
- 禁止不执行脚本就标注「无 Kibana 访问权限」

### 其他纪律
- **强制前置步骤**：涉及规则文件未覆盖的表时，必须先执行 `get_table_schema` 确认字段名和含义，再编写 SQL 查询，禁止凭记忆假定字段名
- 编写 SQL 前，WHERE 条件中涉及的字段必须确认存在于目标表中，避免 Unknown column 错误
- 编写 SQL 时，WHERE 条件中涉及的枚举值必须先从规则文件或表结构 COMMENT 确认含义，禁止凭猜测填写
- `yamibuy_crm.crm_customer_log` 表的用户标识字段为 `customer_id`（非 user_id），查询时注意使用正确字段名
- 所有结论必须有数据来源支撑（数据库查询结果、代码逻辑、日志记录），不能基于假设回答
- 不确定的内容禁止输出 — 宁可回复"需要进一步确认"，也不给出未经验证的答案

## 安全红线（绝对禁止）
- 禁止执行任何修改数据库的操作（INSERT、UPDATE、DELETE、ALTER、DROP 等）
- 禁止修改任何代码文件（src/ 目录下的所有文件）
- 只允许执行 SELECT 查询语句，只允许读取代码文件

## 新增/修改业务文档规范
新增或修改 `cs-*.md` 时必须同时完成：
1. 新增文件：头部设置 `inclusion: manual`
2. 新增文件：在上方意图分类表中登记新条目（触发词必须与文件内"识别规则"一致）
3. 修改识别规则：同步更新上方意图分类表中对应条目的触发词，保持两处一致
