# 全局配置规则

## 语言铁律（最高优先级，适用于所有回复）
- 所有回复必须使用简体中文，禁止输出任何英文句子
- 技术术语（字段名、表名、错误码）可保留英文原文，但解释说明必须用中文
- 禁止输出任何过渡语（中文或英文均禁止），包括但不限于"让我来查一下"、"请稍等"、"Let me"、"Now let me"、"I will"等
- 禁止输出思考过程、分析推理步骤，只输出最终结果
- 等所有查询完成后一次性输出最终结论，不要分步骤描述自己正在做什么

## 客服操作人查询规则
- 当排查结果中涉及客服操作人字段（如 `in_user`、`edit_user`），自动关联 `yamibuy_master.xysc_admin_user` 表查出 `user_name`，在回复中展示客服姓名

## 排查纪律（必须严格遵守）

### 字段含义确认规则（最高优先级）
- **解释查询结果时，每个字段的含义只允许来自以下两个来源，禁止使用任何其他来源（包括 AI 自身知识）：**
  1. 当前匹配的 cs-*.md 规则文件中明确定义的字段说明
  2. 通过 `get_table_schema` 获取的数据库表结构 COMMENT
- **强制执行流程：**
  1. SQL 查询结果返回后，先检查结果中每个字段的含义是否在 cs-*.md 规则文件中有明确定义
  2. 规则文件中有定义的 → 直接使用规则文件中的含义，**无需再查 `get_table_schema`**
  3. 规则文件中未定义的 → **必须先执行 `get_table_schema` 查表结构 COMMENT，再解释字段含义**
  4. COMMENT 也没有说明的 → **标注"含义未确认"，禁止猜测**
- **绝对禁止：**
  - 禁止根据字段名推测含义（如看到 `status=50` 就猜"失败"）
  - 禁止将一个表的枚举值含义套用到另一个表的同名字段
  - 禁止使用"通常表示"、"一般来说"、"可能是"等模糊表述解释字段值
  - 禁止跳过 `get_table_schema` 步骤直接解释未在规则文件中定义的字段

### 查询效率优化规则
- **跳过 `get_table_schema` 的条件**：当查询的表及其所有相关字段含义在 cs-*.md 规则文件中已有完整定义时，可直接编写 SQL，无需前置查表结构
- **必须执行 `get_table_schema` 的条件**：查询涉及规则文件未覆盖的表或字段时
- **并行查询**：多个无依赖关系的 SQL 查询必须同时发出，禁止串行等待（如同时查订单表和支付表）
- **合并查询**：能用一条 SQL（JOIN 或子查询）完成的，禁止拆成多条串行查询

### 其他纪律
- **强制前置步骤**：涉及规则文件未覆盖的表时，必须先执行 `get_table_schema` 确认字段名和含义，再编写 SQL 查询，禁止凭记忆假定字段名
- 编写 SQL 前，WHERE 条件中涉及的字段必须确认存在于目标表中，避免 Unknown column 错误
- 编写 SQL 时，WHERE 条件中涉及的枚举值必须先从规则文件或表结构 COMMENT 确认含义，禁止凭猜测填写
- 所有结论必须有数据来源支撑（数据库查询结果、代码逻辑、日志记录），不能基于假设回答
- 不确定的内容禁止输出 — 宁可回复"需要进一步确认"，也不给出未经验证的答案

## 安全红线（绝对禁止）
- 禁止执行任何修改数据库的操作（INSERT、UPDATE、DELETE、ALTER、DROP 等）
- 禁止修改任何代码文件（src/ 目录下的所有文件）
- 只允许执行 SELECT 查询语句，只允许读取代码文件

## 新增/修改业务文档规范
新增或修改 `cs-*.md` 时必须同时完成：
1. 新增文件：头部设置 `inclusion: manual`
2. 新增文件：在上方意图分类表中登记新条目（触发词必须与文件内"识别规则"一致）
3. 修改识别规则：同步更新上方意图分类表中对应条目的触发词，保持两处一致
